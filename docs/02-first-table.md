# Первая таблица Iceberg

В этой главе вы создадите таблицу и посмотрите, из чего она состоит. Главная мысль Iceberg: таблица - это не файл и не объект в базе данных, а три вещи вместе:

1. **файлы данных** в формате Parquet в хранилище S3;
2. **файлы метаданных** там же, рядом: какие файлы данных входят в таблицу, её схема, история изменений;
3. **запись в каталоге**, которая указывает на текущий файл метаданных.

Trino, Spark или любой другой движок сначала спрашивает каталог, где таблица, потом читает метаданные и только после этого - нужные файлы данных.

Всё в этой главе выполняется под пользователем `engineer`. Как подключиться - в [01-dbeaver.md](01-dbeaver.md).

## Шаг 1. Тестовые данные

В Trino встроен каталог `tpch`. Он не хранит данные, а генерирует их на лету по стандарту бенчмарка TPC-H: заказы, клиенты, товары, поставщики. Скачивать ничего не нужно.

```sql
SELECT * FROM tpch.tiny.orders LIMIT 10;
```

Схемы в `tpch` отличаются объёмом: в `tiny.orders` 15 тысяч строк, в `sf1.orders` 1,5 миллиона, в `sf10` в десять раз больше. Для первых опытов хватит `tiny`.

## Шаг 2. Создать схему и таблицу

```sql
CREATE SCHEMA lakekeeper.sales;

CREATE TABLE lakekeeper.sales.orders
WITH (partitioning = ARRAY['year(orderdate)'])
AS SELECT * FROM tpch.tiny.orders;
```

Вторая команда создаёт таблицу Iceberg и сразу заполняет её данными из `tpch`. `partitioning` раскладывает строки по файлам в зависимости от года в колонке `orderdate`: заказы 1992 года в одни файлы, 1993 года в другие и так далее. Запрос с условием на дату потом читает только файлы нужных лет.

Проверка:

```sql
SELECT orderstatus, count(*) FROM lakekeeper.sales.orders GROUP BY 1;
```

## Шаг 3. Таблица в каталоге

Откройте UI Lakekeeper http://localhost:8181/ui (вход `engineer` / `engineer`), слева выберите Warehouses и пройдите по дереву: `demo` → `sales` → `orders`.

У таблицы несколько вкладок:

| Вкладка | Что там |
|---|---|
| DETAILS | схема таблицы (колонки и типы), разбивка на партиции, свойства, расположение в S3 |
| PREVIEW | первые строки данных |
| VERSIONING | история снимков таблицы |
| FILES | файлы таблицы |
| PERMISSIONS | кому и какие права выданы на таблицу, о ней глава [03-access.md](03-access.md) |

Предпросмотр на вкладке PREVIEW показывает DuckDB, который работает прямо в браузере: каталог выдаёт браузеру адрес файлов и временный ключ к S3, и браузер читает Parquet сам. Поэтому в стенде у хранилища S3 адрес `rustfs.localhost:9100`, одинаковый внутри Docker и в браузере.

## Шаг 4. Таблица в хранилище S3

Откройте консоль RustFS http://localhost:9101 (вход `rustfsadmin` / `rustfs-lab-secret`), бакет `warehouse`, папка `demo`.

Внутри будет папка вида `orders-062b925b...`. Это и есть таблица. Имя строится из названия таблицы и случайного идентификатора, поэтому две таблицы `orders` в разных схемах, как и пересозданная таблица с тем же именем, не попадут в одну папку.

Папки для схемы `sales` нет, таблица лежит прямо в папке warehouse. Это не требование Iceberg: спецификация не говорит, как раскладывать файлы по папкам, в метаданных записан полный путь к каждому файлу. Раскладку выбирают каталог и движок. Lakekeeper начиная с версии 0.13 по умолчанию не создаёт папок для схем, а Trino добавляет к имени таблицы идентификатор (настройка `iceberg.unique-table-location`, по умолчанию включена). Если нужна иерархия "схема - таблица", у warehouse в Lakekeeper есть настройка `storage-layout` со значением `full-hierarchy`, см. [документацию Lakekeeper](https://docs.lakekeeper.io/docs/0.13.x/storage/). Схема при этом всё равно остаётся понятием каталога: папки нужны человеку, который смотрит в бакет, Iceberg находит файлы по путям из метаданных.

В папке таблицы две подпапки.

**`data/`** - файлы данных. Они разложены по партициям: `orderdate_year=1992/`, `orderdate_year=1993/` и так далее, в каждой файл `.parquet`. Это обычные Parquet-файлы, их можно скачать и открыть любым инструментом, который понимает Parquet.

**`metadata/`** - всё, что делает набор Parquet-файлов таблицей:

| Файл | Что это |
|---|---|
| `00000-....gz.metadata.json`, `00001-...`, ... | состояние таблицы: схема, партиции, список снимков, ссылка на текущий снимок. Каждое изменение таблицы создаёт новый такой файл, каталог хранит ссылку на последний. `.gz` - файл сжат |
| `snap-<номер снимка>-....avro` | список манифестов (manifest list) одного снимка |
| `...-m0.avro`, `...-m1.avro` | манифесты: перечень файлов данных с их статистикой (сколько строк, минимум и максимум по каждой колонке). По этой статистике движок пропускает файлы, где заведомо нет нужных строк |
| `....stats` | дополнительная статистика для планировщика запросов (формат Puffin) |

Цепочка чтения выглядит так:

```
каталог -> metadata.json -> список манифестов снимка -> манифесты -> файлы Parquet
```

## Шаг 5. То же самое через SQL

Всё, что вы видели в S3, Trino показывает служебными таблицами. Их имя - имя таблицы и суффикс через `$`, в двойных кавычках.

Где лежит таблица и как она устроена:

```sql
SHOW CREATE TABLE lakekeeper.sales.orders;
```

В ответе будет `location = 's3://warehouse/demo/orders-...'` - та самая папка из шага 4.

Файлы данных и их размер:

```sql
SELECT file_path, record_count, file_size_in_bytes
FROM lakekeeper.sales."orders$files";
```

Партиции:

```sql
SELECT partition, record_count, file_count
FROM lakekeeper.sales."orders$partitions"
ORDER BY 1;
```

Значение партиции здесь будет числом вроде `22`, а не `1992`. Преобразование `year` хранит год как число лет от 1970. В именах папок в S3 Trino пишет привычный год.

Снимки:

```sql
SELECT committed_at, snapshot_id, operation, summary['added-records'] AS added
FROM lakekeeper.sales."orders$snapshots";
```

## Шаг 6. Что меняется при записи

Добавьте строки:

```sql
INSERT INTO lakekeeper.sales.orders
SELECT * FROM tpch.tiny.orders WHERE orderdate >= DATE '1998-01-01';
```

И снова посмотрите на снимки, файлы и папку в S3:

```sql
SELECT committed_at, operation, summary['added-records'] AS added
FROM lakekeeper.sales."orders$snapshots";

SELECT count(*) FROM lakekeeper.sales."orders$files";
```

Появился новый снимок с операцией `append`, в папке `orderdate_year=1998/` второй файл Parquet, в `metadata/` новый `metadata.json` и новые манифесты. Старые файлы при этом не изменились.

Это основное свойство Iceberg: файлы никогда не переписываются на месте. Любое изменение добавляет новые файлы и новый снимок, а каталог переключает ссылку на новый `metadata.json` одной атомарной операцией. Поэтому читатели не видят таблицу в промежуточном состоянии, а к старым снимкам можно вернуться - об этом глава [04-snapshots.md](04-snapshots.md).

Обратная сторона - со временем копятся мелкие файлы, старые снимки и файлы, на которые уже ничто не ссылается. Как их убирать - в главе [05-maintenance.md](05-maintenance.md).

## Что запомнить

- Таблица Iceberg - это файлы Parquet, файлы метаданных рядом с ними и запись в каталоге.
- Схема (`sales`) - понятие каталога. Папки в S3 у неё по умолчанию нет, раскладку файлов задаёт каталог (`storage-layout` в Lakekeeper).
- Каждая запись создаёт новый снимок и новые файлы, старые не меняются.
- Служебные таблицы `$files`, `$partitions`, `$snapshots` показывают устройство таблицы через обычный SQL.
